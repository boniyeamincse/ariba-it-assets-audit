# Software Requirement & Technical Specification (SRS)

## Project Name: Enterprise IT Asset Audit & Multi-Location Inventory System
**Organization Context:** Akij Plastics Ltd & Sister Concerns (Akij Group)  
**Target Architecture:** Python Django (Backend & Admin) + Django Templates with Modern HTML5/TailwindCSS (Frontend UI)  
**Target Audience:** Management / "Sir", Super Admin, HO Admin, Factory Admin, Depot Admin  

---

## ১. ভূমিকা ও লক্ষ্য (Introduction & Executive Objective)

### ১.১ লক্ষ্য (Objective)
প্রতিষ্ঠানটির বিভিন্ন ধরণের ভৌগোলিক লোকেশন—যেমন: **Head Office**, বিভিন্ন উৎপাদন কেন্দ্র (**Factories** যেমন: *APL Factory Chattak*), এবং দেশব্যাপী বিস্তৃত ডেলিভারি পয়েন্ট (**Depots**)—এ থাকা সমস্ত IT Assets (Infrastructure ও End-User Devices)-এর সঠিক হিসাব রাখা, স্বয়ংক্রিয় অডিট সম্পন্ন করা এবং ম্যানেজমেন্টের ("Sir") সামনে রিয়েল-টাইম সিদ্ধান্ত গ্রহণের উপযোগী এক্সিকিউটিভ রিপোর্ট ও অ্যানালিটিক্স উপস্থাপন করা।

### ১.২ মূল চ্যালেঞ্জ ও সমাধান
1. **বহুমাত্রিক লোকেশন:** প্রধান কার্যালয়, কারখানা এবং ডিপোসমূহের আইটি ডিভাইসের ধরন ও সংখ্যা ভিন্ন।
2. **অ্যাক্টিভ বনাম ব্যাকআপ হিসাব:** অনেক সাইটে অতিরিক্ত ব্যাকআপ ডিভাইস (Backup Laptop, Backup Monitor, Backup Printer) থাকে যা অডিটে আলাদাভাবে গণনা করা জরুরি।
3. **ফিল্ড অডিট ডেটা সিঙ্ক:** দূরবর্তী ডিপো বা কারখানায় ইন্টারনেট না থাকলেও অফলাইনে JSON আকারে ডেটা এন্ট্রি নেওয়া এবং পরবর্তীতে সেন্ট্রাল সিস্টেমে সিঙ্ক করা।
4. **ম্যানেজমেন্ট রিপোর্টিং:** এক ক্লিকে অফিশিয়াল সিল-স্বাক্ষর সম্বলিত PDF এবং এক্সেল (.xlsx) রিপোর্ট তৈরি।

## ৩. ইউজার রোল ও পারমিশন ম্যাট্রিক্স (User Roles & Permissions)

| রোল (Role) | লোকেশন অ্যাক্সেস | অনুমতি ও দায়িত্ব |
| :--- | :--- | :--- |
| **Super Admin** | সিস্টেম প্রশাসনের জন্য পূর্ণ অ্যাক্সেস। | HO Admin অ্যাকাউন্ট, রোল ও সিস্টেম সেটিংস পরিচালনা এবং জরুরি প্রশাসনিক কাজ। |
| **HO Admin** | সব কোম্পানির Head Office, Factory ও Depot। | নতুন লোকেশন যোগ ও পরিচালনা, Factory Admin ও Depot Admin-কে লোকেশন অ্যাসাইন, মাস্টার ডিভাইস ক্যাটালগ পরিচালনা, অডিট যাচাই ও চূড়ান্ত অনুমোদন, কেন্দ্রীয় ড্যাশবোর্ড এবং JSON, Excel ও PDF রিপোর্ট। দৈনন্দিন পরিচালনার রোলগুলোর মধ্যে শুধু HO Admin সব লোকেশন দেখতে পারবে। |
| **Factory Admin** | HO Admin যে Factory লোকেশনগুলো অ্যাসাইন করেছে। | নিজের লোকেশনের ডিভাইস কাউন্ট ও রিমার্কস এন্ট্রি, অডিট তৈরি ও সাবমিট, JSON ইমপোর্ট ও এক্সপোর্ট, ড্যাশবোর্ড ও রিপোর্ট দেখা, Excel ও PDF ডাউনলোড। |
| **Depot Admin** | HO Admin যে Depot লোকেশনগুলো অ্যাসাইন করেছে। | নিজের লোকেশনে Factory Admin-এর মতো একই কাজের অনুমতি। |

### ৩.১ লোকেশন অ্যাসাইনমেন্ট ও অ্যাক্সেস যাচাই

* Factory Admin-কে `FACTORY` এবং Depot Admin-কে `DEPOT` ধরনের এক বা একাধিক লোকেশন অ্যাসাইন করা যাবে। লোকেশন অ্যাসাইন না থাকলে ওই অ্যাডমিন কোনো লোকেশনের ডেটা অ্যাক্সেস করতে পারবে না।
* লোকেশন তালিকা, ড্যাশবোর্ড, অডিট দেখা বা পরিবর্তন, সরাসরি URL, JSON ইমপোর্ট এবং সব রিপোর্ট এক্সপোর্টে সার্ভার ব্যবহারকারীর রোল ও লোকেশন অ্যাসাইনমেন্ট যাচাই করবে। JSON ফাইলের লোকেশনও ব্যবহারকারীর অনুমোদিত লোকেশনের মধ্যে থাকতে হবে।

### ৩.২ অডিট যাচাই ও অনুমোদন

* Factory Admin বা Depot Admin নিজের লোকেশনের অডিট সাবমিট করলে HO Admin যাচাই করবে। HO Admin হেড অফিসের অডিটও তৈরি ও সাবমিট করতে পারবে। স্ট্যাটাসের ক্রম `DRAFT` → `SUBMITTED` → `VERIFIED` → `APPROVED`।
* সংশোধনের প্রয়োজন হলে HO Admin মন্তব্যসহ অডিট `DRAFT`-এ ফেরত পাঠাবে। যাচাইয়ের পর HO Admin চূড়ান্ত অনুমোদন দেবে। যিনি অডিটটি সাবমিট করেছেন, তিনি সেটি অনুমোদন করতে পারবেন না।

### ৩.৩ অ্যাডমিন ড্যাশবোর্ড রাউট

`/admin/dashboard/` সব অ্যাডমিনের সাধারণ প্রবেশপথ। লগইন করা ব্যবহারকারীকে সার্ভার তার রোলের ড্যাশবোর্ডে পাঠাবে। লগইন করা না থাকলে লগইন পেজে পাঠাবে।

| রোল | ড্যাশবোর্ড URL |
| :--- | :--- |
| **Super Admin** | `/admin/super/dashboard/` |
| **HO Admin** | `/admin/ho/dashboard/` |
| **Factory Admin** | `/admin/factory/dashboard/` |
| **Depot Admin** | `/admin/depot/dashboard/` |

সরাসরি ড্যাশবোর্ড URL খুললেও সার্ভার লগইন ও রোল যাচাই করবে। Factory Admin ও Depot Admin-এর ড্যাশবোর্ডে শুধু অ্যাসাইন করা লোকেশনগুলোর তথ্য থাকবে। Django URLconf-এ এই রাউটগুলো `admin.site.urls`-এর আগে নিবন্ধন করতে হবে।

## ৪. সিস্টেমের মূল মডিউলসমূহ (Core Modules)

### মডিউল ১: অথেনটিকেশন ও ইউজার ম্যানেজমেন্ট (Authentication & Security)
* ইউজার লগইন, লগআউট, পাসওয়ার্ড রিসেট ও সেশন টাইমআউট।
* রোল ও লোকেশন অ্যাসাইনমেন্ট অনুযায়ী পারমিশন (Role-Based and Location-Scoped Access)।
* প্রতিটি অডিট এন্ট্রির সাথে `created_by`, `updated_by` এবং টাইমস্ট্যাম্প ট্র্যাক রাখা।

### মডিউল ২: মাল্টি-লোকেশন ও অর্গানাইজেশন হায়ারার্কি (Location & Unit Management)
* **Company / Unit:** (যেমন: *Akij Plastics Ltd*, *Akij Jute Mills Ltd*)
* **Location Types:**
  1. **Head Office** (কর্পোরেট অফিস, ডেটাসেন্টার)
  2. **Factories** (যেমন: *APL Factory Chattak*, *Factory Unit-1*, *Unit-2*)
  3. **Depots / Regional Warehouses** (বগুড়া, চট্টগ্রাম, সিলেট, যশোর ডিপো ইত্যাদি)
* প্রতিটি লোকেশনের দায়িত্বপ্রাপ্ত ইন-চার্জ, ঠিকানা এবং যোগাযোগের বিবরণ।
* HO Admin লোকেশন তৈরি করবে এবং সংশ্লিষ্ট Factory Admin বা Depot Admin-কে অ্যাসাইন করবে।

### মডিউল ৩: ডিভাইস ক্যাটালগ ও ক্যাটাগরি ম্যানেজমেন্ট (Device Catalog Master)
ডিভাইসগুলোকে প্রধানত দুটি মূল ক্যাটাগরিতে ভাগ করা হয়েছে:
1. **Infrastructure Assets:**
   * Microtik / Cisco Router
   * Core Switch, Managed Switch, Unmanaged Switch
   * Server / Desktop Server / NAS
   * Network Rack, UniFi AP / WiFi AP
   * NVR / DVR, IP Camera, CCTV Monitor
   * Online UPS / IPS Full Set
   * Access Control (Biometric / Face Recognition)
   * PA System Controller, Remote Mic Controller, Sound Box
2. **User / End-User Devices:**
   * Laptop, Desktop PC, All-in-One PC, Mini PC, MacBook
   * Monitor (TFT / LED), Backup Monitor
   * Printers: Laser Printer, Colour Printer, MRP Printer, Voucher Printer, Dotmatrix VAT Printer, Card Printer, Backup Printer
   * Scanners: Flatbed Scanner, Speed / High-Speed Scanner, Backup Scanner
   * Peripherals: USB Mouse, USB Keyboard, USB Hub, Headphone, Webcam, Projector, Smart TV

### মডিউল ৪: ফিজিক্যাল অডিট ও ডেটা এন্ট্রি ইঞ্জিন (Physical Audit & Stock Count Engine)
* **সেশন ভিত্তিক অডিট:** অডিট তারিখ ধরে সেশন তৈরি করা যাবে। কোয়ার্টার বা বছরের হিসাব তারিখ দিয়ে ফিল্টার করা যাবে।
* **ডায়নামিক এন্ট্রি ফর্ম (Django Formset):**
  * একই স্ক্রিনে Infrastructure ও User Devices ট্যাবে আলাদা এন্ট্রি।
  * স্ট্যাটাস ফিল্ডস: `In-Use (Active)`, `Backup / Spare`, `Faulty / Damaged`।
  * রিয়েল-টাইম ক্যালকুলেশন: অটোমেটিক মোট সংখ্যা (`Total = In-Use + Backup + Faulty`) হিসাব।
  * রিমার্কস বা নোট যুক্ত করার সুবিধা।
* **বাল্ক এন্ট্রি শর্টকাট:** কিবোর্ড দিয়ে দ্রুত ট্যাব চেপে এক রো থেকে অন্য রোতে যাওয়ার সুবিধা।

### মডিউল ৫: অফলাইন সিঙ্ক ও JSON ইমপোর্ট/এক্সপোর্ট (JSON Engine)
* যেসব ফ্যাক্টরি বা ডিপোতে অডিটের সময় নেটওয়ার্ক থাকবে না, সংশ্লিষ্ট অ্যাডমিন ল্যাপটপে অফলাইন ফর্ম বা JSON ব্যবহার করবেন।
* **Export JSON:** অ্যাক্সেস আছে এমন লোকেশনের অডিট ডেটা `.json` ফাইল হিসেবে ডাউনলোড করা যাবে।
* **Import JSON:** সেন্ট্রাল সিস্টেমে `.json` আপলোড করলে লোকেশন অ্যাক্সেস যাচাইয়ের পর অডিট রেকর্ড আপডেট হবে।

### মডিউল ৬: এক্সিকিউটিভ ড্যাশবোর্ড ও ভিজ্যুয়াল অ্যানালিটিক্স (Executive Dashboard)
* **KPI Metrics Cards:**
  * মোট অডিটকৃত লোকেশন সংখ্যা।
  * সমগ্র প্রতিষ্ঠানে মোট আইটি ইকুইপমেন্ট সংখ্যা (Grand Total Count)।
  * মোট চালু ডিভাইস বনাম ব্যাকআপ ডিভাইস বনাম নষ্ট ডিভাইস।
  * মোট আইপি ক্যামেরা ও নেটওয়ার্ক ডিভাইসের সংখ্যা।
* **গ্রাফিক্যাল চার্টস (Chart.js):**
  * *Location-wise Asset Distribution (Bar Chart)*
  * *Infrastructure vs User Devices (Donut Chart)*
  * *Printer Inventory Breakdown (Pie Chart)*

### মডিউল ৭: মাস্টার কম্প্যারিজন ম্যাট্রিক্স ও রিপোর্টিং (Reporting Engine for Sir)
* **Master Cross-Tab Matrix:**
  * বামে ডিভাইসের নাম, উপরে কলামে [Head Office | Chattak Factory | Depot 1 | Depot 2 ...] এবং ডানে [Total]।
  * HO Admin পুরো প্রতিষ্ঠানের তুলনামূলক হিসাব দেখতে পারবে। Factory Admin ও Depot Admin-এর ম্যাট্রিক্সে তাদের অ্যাসাইন করা লোকেশনগুলোর হিসাব থাকবে।
* **অফিশিয়াল এক্সিকিউটিভ প্রিন্ট ভিউ (Print / PDF):**
  * Akij লোগো ও হেডার।
  * অডিট সাবমিটকারী অ্যাডমিনের স্বাক্ষর, লোকেশন ইন-চার্জের স্বাক্ষর এবং HO Admin-এর চূড়ান্ত অনুমোদনের স্থান।
* **Excel Export (.xlsx):**
  * অ্যাক্সেস আছে এমন লোকেশনের ফিল্টার করা ডেটা স্ট্যান্ডার্ড ফরমেটেড এক্সেলে ডাউনলোড।

### মডিউল ৮: অডিট হিস্টোরি ও ডিসক্রিপেন্সি ট্র্যাকিং (Discrepancy & Variance Analysis)
* আগের অডিটের সাথে বর্তমান অডিটের তুলনা:
  * গত অডিটের তুলনায় কোন ডিভাইসের সংখ্যা বাড়ল বা কমল (যেমন: ৫টি ল্যাপটপ স্থানান্তরিত হয়েছে বা কমেছে)।
  * মিসিং বা ড্যামেজড ডিভাইসের বিশেষ ফ্ল্যাগিং।

## ৬. ডাইনামিক আচরণ ও ডেটা মডেল

### ৬.১ কোম্পানি, লোকেশন, ক্যাটালগ ও অ্যাসাইনমেন্ট

* HO Admin অ্যাপ থেকে কোম্পানি, লোকেশন এবং ডিভাইস টাইপ যোগ, সম্পাদনা ও নিষ্ক্রিয় করতে পারবে। লোকেশন তৈরি করার সময় কোম্পানি বেছে নেবে। একই কোম্পানির মধ্যে বৈধ parent location নির্বাচন করা যাবে। নিজের অধীনে নিজেকে বা নিজের কোনো শাখাকে বসানো যাবে না।
* লোকেশনের `code` ইমপোর্ট ও এক্সপোর্টের পরিচয় হিসেবে স্থায়ী থাকবে। নাম, ঠিকানা, যোগাযোগের তথ্য বা স্ট্যাটাস বদলানো যাবে। ক্যাটালগে প্রতিটি ডিভাইস টাইপের জন্য একটি স্থায়ী কোড যোগ করতে হবে।
* সক্রিয় কোম্পানি, লোকেশন ও ক্যাটালগ ডেটাবেজ থেকে ফর্ম ও ফিল্টারে আসবে। নতুন লোকেশন বা ডিভাইস যোগ করতে টেমপ্লেট, JavaScript বা seed script পরিবর্তনের প্রয়োজন হবে না। নিষ্ক্রিয় রেকর্ড নতুন অডিটের নির্বাচনে থাকবে না। পুরোনো অডিট ও রিপোর্টে সংশ্লিষ্ট তথ্য দেখা যাবে।
* Factory Admin এবং Depot Admin-এর জন্য ব্যবহারকারী ও লোকেশনের অ্যাসাইনমেন্ট রেকর্ড থাকবে। HO Admin অ্যাসাইন বা প্রত্যাহার করলে পরের রিকোয়েস্ট থেকেই তালিকা, ড্যাশবোর্ড ও ডাউনলোডে তা কার্যকর হবে। Parent location অ্যাসাইন করলে তার child location-এর অ্যাক্সেস স্বয়ংক্রিয়ভাবে যোগ হবে না।
* Location মডেলে বর্তমানে Warehouse ও Branch ধরনের রেকর্ডও আছে। স্থানীয় রোল নির্ধারিত না হওয়া পর্যন্ত HO Admin সেগুলো পরিচালনা করবে।

### ৬.২ রেকর্ড ও সম্পর্ক

| রেকর্ড | সম্পর্ক ও নিয়ম |
| :--- | :--- |
| `User`, `UserProfile`, লোকেশন অ্যাসাইনমেন্ট | একজন ব্যবহারকারীর নির্ধারিত অপারেশনাল রোল থাকবে। একটি স্থানীয় প্রোফাইল একাধিক অনুমোদিত লোকেশনের সঙ্গে যুক্ত হতে পারবে। একই ব্যবহারকারী ও লোকেশনের জোড়া একবারই থাকবে। Django superuser সুবিধা টেকনিক্যাল Super Admin-এর জন্য। |
| `Company`, `Location` | একটি কোম্পানির একাধিক লোকেশন ও লোকেশনের ঐচ্ছিক parent থাকবে। অডিট থাকা লোকেশন মুছে ফেলার পরিবর্তে নিষ্ক্রিয় করে ইতিহাস সংরক্ষণ করতে হবে। |
| `DeviceCategory`, `DeviceType` | ক্যাটাগরি ও টাইপ থেকে অডিট ফর্মের সারি তৈরি হবে। নতুন অডিটে মূল ডিভাইস টাইপের `backup_qty`-তে ব্যাকআপ গণনা হবে। পুরোনো `Backup Laptop`-এর মতো সারি যাচাই করে ম্যাপ করতে হবে। ঐতিহাসিক কাউন্ট একবারই গণনা হবে। |
| `AuditSession` | প্রতি লোকেশন ও অডিট তারিখে একটি সেশন। স্ট্যাটাসের সঙ্গে সাবমিট, যাচাই, ফেরত ও অনুমোদনের ব্যবহারকারী, সময় এবং প্রযোজ্য মন্তব্য সংরক্ষণ করতে হবে। |
| `AuditItem` | প্রতি সেশন ও ডিভাইস টাইপে একটি সারি। `active_qty`, `backup_qty` ও `faulty_qty` শূন্য বা ধনাত্মক পূর্ণসংখ্যা হবে। সার্ভার যোগ করে `total_qty` নির্ধারণ করবে। |
| অডিট ইতিহাস ও কার্যক্রম লগ | অডিট স্ট্যাটাস ও অনুমতি পরিবর্তনের ঘটনায় সংশ্লিষ্ট ব্যবহারকারী, সময় ও রেকর্ড সংরক্ষণ করতে হবে। কেন্দ্রীয় লগ HO Admin এবং টেকনিক্যাল Super Admin-এর জন্য। স্থানীয় অ্যাডমিন নিজের অ্যাসাইন করা লোকেশনের অডিট ইতিহাস দেখবে। |

সোর্সের বর্তমান মডেলগুলো `apps/accounts/`, `apps/locations/`, `apps/devices/`, `apps/audits/` এবং `apps/common/`-এ আছে। উপরের টেবিল বাস্তবায়নের লক্ষ্য, এতে নতুন অ্যাসাইনমেন্ট ও অডিট ইতিহাসের প্রয়োজনীয়তাও অন্তর্ভুক্ত।

### ৬.৩ দৈনন্দিন অডিট

1. অ্যাডমিন লগইন করলে `/admin/dashboard/` থেকে নিজের রোলের ড্যাশবোর্ডে যাবে। নতুন অডিটে অনুমোদিত সক্রিয় লোকেশন, অডিট তারিখ এবং ক্যাটালগের ডিভাইস দেখাবে।
2. অ্যাডমিন ডিভাইসের গণনা ও মন্তব্য লিখে খসড়া সংরক্ষণ বা সাবমিট করবে। ভুল ইনপুটে ফিল্ডভিত্তিক বার্তা এবং দেওয়া মান দেখাতে হবে। সেশন, আইটেম ও সংশ্লিষ্ট পরিবর্তন এক ট্রানজ্যাকশনে সংরক্ষণ করতে হবে। একই লোকেশন ও তারিখের সেশন থাকলে সেই রেকর্ড দেখাবে। পুরোনো ফর্ম থেকে নতুন পরিবর্তন ওভাররাইট করার আগে সংঘাত জানাবে।
3. HO Admin সাবমিট করা অডিট দেখে যাচাই করবে বা মন্তব্যসহ খসড়ায় ফেরত দেবে। যাচাইয়ের পর অনুমোদন হবে। রোল, বর্তমান স্ট্যাটাস এবং সাবমিটকারী যাচাই করে সার্ভার প্রতিটি পরিবর্তন কার্যকর করবে।
4. সাবমিটের পর সাধারণ কাউন্ট সম্পাদনা বন্ধ থাকবে। ফেরত দিলে খসড়া আবার সম্পাদনা করা যাবে। অনুমোদিত অডিটের সংশোধন বা পুনরায় খোলার পদ্ধতি চূড়ান্ত হওয়া পর্যন্ত ওই সেশন এডিট ও ইমপোর্ট থেকে সুরক্ষিত থাকবে।

### ৬.৪ অফলাইন JSON ও পুরোনো ডেটা

* অফলাইন ফর্ম ও ক্যাটালগ আগে প্রস্তুত করে নিতে হবে। সংযোগ ছাড়া লোকাল ডিভাইসে ডেটা এন্ট্রি ও JSON সেভ করা যাবে। সংযোগ ফিরে এলে লগইন করে অনুমোদিত লোকেশনে ইমপোর্ট করা যাবে।
* নতুন ফাইলে `schema_version`, `location_code`, `audit_date` এবং ডিভাইসের স্থায়ী কোডসহ `active`, `backup`, `faulty` ও `remarks` থাকবে। আগের খসড়া থেকে তৈরি হলে তার রিভিশনও থাকবে। সার্ভার মোট গণনা ও অ্যাক্সেস ঠিক করবে।
* ইমপোর্টে আগে প্রিভিউ দেখাতে হবে। সেখানে লোকেশন, তারিখ, বদলানো সারি ও ভুল দেখাবে। অচেনা কোড, ভুল সংখ্যা, ডুপ্লিকেট ডিভাইস বা বদলে যাওয়া খসড়ায় ইমপোর্ট থামবে। ফাইলের পরিচয়, স্ট্যাটাস বা নাম থেকে অনুমোদন দেওয়া যাবে না।
* নিশ্চিত করার পর ফাইলে থাকা সারিগুলো খসড়ায় এক ট্রানজ্যাকশনে সেভ হবে। ফাইলে অনুপস্থিত সারি অপরিবর্তিত থাকবে। কোনো কাউন্ট শূন্য করতে হলে সেই সারিতে শূন্য পাঠাতে হবে। একই ফাইল পুনরায় আপলোডে ডুপ্লিকেট সেশন বা কাউন্ট তৈরি হবে না। প্রিভিউয়ের পরে রেকর্ড বদলালে আবার যাচাই করতে হবে।
* `data/it_audit_data.json`-এর পুরোনো `locations[]` এবং শুধু `qty` থাকা সারির জন্য ম্যাপিং প্রয়োজন। ব্যাকআপ বা নষ্ট সংখ্যার তথ্য অনুপস্থিত থাকলে সেটা প্রিভিউতে দেখাতে হবে। পুরোনো সোর্স থেকে নিশ্চিত হওয়া ছাড়া স্ট্যাটাস ধরে নেওয়া যাবে না।

### ৬.৫ ড্যাশবোর্ড, ম্যাট্রিক্স ও রিপোর্ট

* কোম্পানি, লোকেশনের ধরন, লোকেশন এবং রিপোর্টের শেষ তারিখ দিয়ে ফিল্টার করা যাবে। ফিল্টারের অপশন ও ফলাফল উভয়ই রোলের অ্যাক্সেস মেনে চলবে। লোকেশন ও তারিখ হেডারে দেখাতে হবে।
* প্রস্তাবিত ডিফল্ট হিসাবে রিপোর্টের শেষ তারিখ পর্যন্ত প্রতিটি দৃশ্যমান লোকেশনের সর্বশেষ `APPROVED` সেশন নির্বাচন করতে হবে। সাধারণ স্টক হিসাবে একই লোকেশনের পুরোনো ও নতুন সেশন একসঙ্গে যোগ হবে না। অনুমোদিত সেশন ছাড়া লোকেশনকে ‘অনুমোদিত অডিট নেই’ দেখাতে হবে। ইতিহাস স্ক্রিনে সেশনগুলো আলাদা থাকবে।
* একই ফিল্টারে KPI, ওয়েব ম্যাট্রিক্স ও Excel-এর মোট মিলবে। একক অডিটের প্রিন্ট ও PDF সেই সেশনের স্ট্যাটাস ও ডেটা দেখাবে। ভ্যারিয়েন্স রিপোর্ট একই লোকেশনের সর্বশেষ ও তার আগের অনুমোদিত অডিট তুলনা করবে এবং তুলনার দুটি তারিখ দেখাবে। তারিখ ও প্রদর্শিত সময়ের জন্য `Asia/Dhaka` ব্যবহার করতে হবে।
* ড্যাশবোর্ডে ডেটা বদলালে পরের লোড বা ফিল্টার পরিবর্তনে নতুন হিসাব দেখা যাবে। অডিট ফর্মে টাইপ করার সময় ব্রাউজার কাউন্টের প্রিভিউ দেখাবে। সংরক্ষিত গণনা সার্ভারে হবে।

## ৭. প্রজেক্ট ফোল্ডার ও রাউট (Directory Layout)

```text
audit/
├── manage.py
├── README.md
├── core_project/          # Settings, root URLconf, ASGI ও WSGI
├── apps/
│   ├── accounts/          # Users, profiles, login ও logout
│   ├── common/            # Shared models ও activity logs
│   ├── locations/         # Companies, locations ও location views
│   ├── devices/           # Device catalog models
│   ├── audits/            # Audit sessions, entry, JSON ও print
│   └── reports/           # Dashboard, comparison matrix ও Excel
├── templates/             # Dashboard, accounts, locations, audits, reports ও logs
├── static/
├── data/                 # Legacy JSON ও spreadsheet reference
└── docs/
    └── SOFTWARE_SPECIFICATION.md
```

ধারা ৩.৩-এর ড্যাশবোর্ড রাউট চালু করলে `/` থেকে `/admin/dashboard/`-এ পাঠাতে হবে। বিদ্যমান `/locations/`, `/audits/`, `/matrix/`, `/sync-json/` ও `/logs/` রাউটে একই পারমিশন প্রয়োগ করতে হবে। Django Admin-এর `/admin/` টেকনিক্যাল প্রশাসনের জন্য থাকবে।

## ৯. বাস্তবায়নের আগে চূড়ান্ত করার বিষয়

* **পুরোনো অ্যাকাউন্ট ও লোকেশন ম্যাপিং।** Super Admin ও HO Admin কোন পুরোনো অ্যাকাউন্ট কোন রোল ও লোকেশনে যাবে তা নির্ধারণ করবে। যাচাই না হওয়া অ্যাকাউন্ট সীমিত অ্যাক্সেসে থাকবে।
* **রিপোর্টের সময়সীমা।** HO টিম সর্বশেষ অনুমোদিত অডিটের প্রস্তাবিত ডিফল্ট যাচাই করবে এবং সংশ্লিষ্ট মাস বা কোয়ার্টারের আলাদা রিপোর্ট দরকার কি না ঠিক করবে।
* **অনুমোদিত অডিট সংশোধন।** HO টিম ঠিক করবে সংশোধন নতুন রিভিশন হিসেবে যাবে, নাকি কারণ লিখে অনুমোদন প্রত্যাহারের মাধ্যমে পুনরায় খুলবে।
